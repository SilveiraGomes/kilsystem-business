# E1.05 — Inicialização e ciclo de vida do serviço local

- Estado: concluída
- Autorização: concedida pelo responsável do projecto. Substitui a proposta redigida no fecho de E1.04: serviço Node.js independente do Electron, sem API HTTP, sem acesso remoto e sem integração com a interface.
- Commit: `feat: implement local service lifecycle`
- Ponto de partida: `d713c3c`

## Objectivo

Implementar um serviço local Node.js, independente do processo Electron, que inicialize e encerre correctamente a persistência SQLite de E1.04.

## Comandos do serviço

As variáveis têm de estar definidas no ambiente do processo; nenhum ficheiro `.env` é lido. Exemplo em PowerShell, com uma base de desenvolvimento fora do repositório:

```powershell
pnpm.cmd --filter @kil-business/local-api build   # ou pnpm.cmd build (compila também database e shared-types)
$env:LOCAL_DATABASE_PATH = "$env:LOCALAPPDATA\KIL-Business-dev\kil-local.sqlite"
$env:LOCAL_SERVICE_ENVIRONMENT = "development"
$env:LOCAL_SERVICE_INSTANCE_ID = "dev-local"
$env:LOCAL_SERVICE_ON_MISSING_DATABASE = "create"
$env:LOCAL_SERVICE_ON_PENDING_MIGRATIONS = "apply"
pnpm.cmd --filter @kil-business/local-api start:check   # arranca e encerra (verificação)
pnpm.cmd --filter @kil-business/local-api start         # fica em READY; Ctrl+C para encerrar
```

O directório da base tem de existir; o serviço não cria directórios.

| Objectivo | Comando |
| --- | --- |
| Testar o serviço | `pnpm.cmd test local-service` |
| Testar o serviço e o isolamento através dele | `pnpm.cmd test local-service tenant-isolation` |
| Executar sem pnpm | `node services/local-api/dist/main.js [--check]` |
| Encerrar | `Ctrl+C` (`SIGINT`); também `SIGTERM` e, em Windows, `SIGBREAK` (`Ctrl+Break`) |

## Validação (2026-11-14)

- `pnpm.cmd lint`, `pnpm.cmd typecheck`: sem erros.
- `pnpm.cmd test`: 7 ficheiros, 279 testes aprovados: os 183 anteriores, mais 52 em `local-service` e 44 na suite de contrato através do serviço.
- `pnpm.cmd build`: 12/12 projectos (`services/local-api` compilado depois de `packages/database`).
- `pnpm.cmd check`: código de saída 0.
- `pnpm.cmd --filter @kil-business/desktop test`: 4/4 aprovados.
- `pnpm.cmd --filter @kil-business/desktop smoke`: `KIL_ELECTRON_SMOKE_OK`, código 0. Na validação final voltou a aparecer a mensagem GPU do Chromium no encerramento (PD-13). `apps/desktop` não foi alterado.
- **Execução real a partir de `dist/` em Node puro**, com base em `%TEMP%`:
  - primeiro `start:check` → base criada, migração 1 aplicada, `STOPPED`, código 0;
  - segundo `--check` com política `fail`/`fail` → `appliedMigrations: []`, código 0;
  - caminho dentro do repositório → `service.config_invalid` (`location-inside-protected-directory`), código 2, nenhum ficheiro criado;
  - modo contínuo → processo vivo em `READY` após 4 s; depois de terminação forçada, a base reabre com política estrita sem migrações pendentes.
- **Verificação por mutação** (ficheiro reposto em seguida):

  | Mutação | Resultado |
  | --- | --- |
  | Não fechar a ligação | 60 testes falham |
  | Arranque não idempotente | 1 falha |
  | Não libertar a ligação em arranque falhado | 3 falham |
  | Protecção `READY` enfraquecida | 2 falham |

  Retirar só a condição de estado mantendo `persistence === undefined` é equivalente ao original, porque a persistência só existe em `READY`.
- **Não verificado**: encerramento por `Ctrl+C` numa consola real. Em Windows não é possível enviar `SIGINT` a outro processo de forma programática. O caminho está coberto pelo teste do modo contínuo com sinal injectado.
