## 4. Revisão do código (diff completo lido)

`services/local-api/src/local-service.ts` (`run()`, linhas 504–540; `start()`, linhas 542–563):

- `run()`: `completedStartup = await initialise()`; `logger.log('service.ready')` ainda em `STARTING`; `transition('READY')`; só depois `startupReport = completedStartup; lastFailure = undefined`. Uma falha do *sink* cai no `catch` existente: `LocalServiceStartupError('unexpected', { cause })`, `release()`, `lastFailure`, `STARTING→FAILED` (transição válida). Correcto.
- `start()`: `await stopping` com `try/catch`; só `LocalServiceStopError` com `reason === 'record-failed'` permite prosseguir (`return start()`); tudo o resto é relançado. Correcto: em `shutdown()`, `record-failed` só é lançado depois de `release()` bem-sucedido e de `settleState('STOPPED')`; `release-failed` leva a `FAILED` com posse desconhecida.
- Ordem de microtarefas: o `finally { stopping = undefined }` de `stop()` corre antes da continuação do `start()` (registado primeiro), logo a recursão vê `stopping` limpo e não há laço. Confirmado por execução (I4, I5, I8).
- Concorrência de vários `start()` em espera: o primeiro a retomar define `starting` de forma síncrona; os restantes devolvem a mesma promessa. Confirmado (I4: 3 `start()` → exactamente 1 ligação nova).
- Consumidores da ordem dos registos: nenhum no código de produção (`services/`, `apps/`); só testes (`database-exclusivity`, `local-service`), que passam.
- Sem `any`, sem coerções novas, sem dependências, sem HTTP/IPC, sem dados sensíveis em registos (o *payload* de `service.ready` é o mesmo `StartupReport`).
